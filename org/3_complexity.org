* Introduction to Big-Oh

- Sometimes you need to compare two programs: Not by readibility,
  conciseness, efficiency but by "complexity".

- *Measure 1:* Time complexity - not measured in time units but in the
  number of operations it takes to complete a task. 

- *Measure 2:* Space complexity - memory taken up when it runs.

- This is measured mathematically (using a formula and convergence
  estimates).

* History of O
#+attr_html: :width 250px :float nil:
[[../img/Paul_Bachmann.jpg]]

- *Background*: The "O" in Big-O comes from the German word "Ordnung"
  (Engl. order) introduced by the German mathematician Paul Bachmann
  (1892). It refers to the order of growth of any function.

- "Big-O" is a general asymptotic upper bound notation, e.g.
  + Time complexity = running time as input grows
  + Space complexity = memory usage as input grows
  + I/O complexity = number of disk accesses or cache misses
  + Operation complexity = number of additions, multiplications etc.
  + Circuit complexity = Number of gates/depth of logic circuits

- Applies to any resource cost function f(n) with input size n.
  
* Big O for an array

- Given an array (=1 2 3 4 5 6 7=), and our job is to look for a number:
  Our worst case is looking for number =7=, our best case is looking for
  =1=, and our average case is looking for =4=.

- Why is that?
  #+begin_quote
  These estimates only hold for a linear search - linear in the number
  of elements of the array: we compare each new element with the
  number.

  1. Best case: target is n=1 - 1 comparison

  2. Worst case: target is the last element n=7 - n comparisons

  3. Average case: target can be anywhere - expect
     (1 + 2 + ... + n)/n = (n+1)/2 comparisons.
  #+end_quote

- Terminology:
  #+begin_quote
  1. Best case: \Omega ("Omega")

  2. Worst case: O ("Big-oh")

  3. Average case: \Theta ("Theta")
  #+end_quote

* Linear time complexity: O(n)

- Linear time complexity O(n) is the easiest one to understand.

- The function =printItems= prints a loop index =i= exactly =n= times - it's
  O(n).
  #+name: O(n)
  #+begin_src C++ :main no :includes :results output :exports both
    #include <iostream>
    using namespace std;

    void printItems(int n)
    {
      for (int i = 0; i < n; i++)
        {
          cout << (i + 1) << " ";
        }
    }

    int main()
    {
      printItems(10); // n = 10
      return 0;
    }
  #+end_src

* Drop constant terms

- We're going to modify another ~for~ loop *serially*, after the first:
  #+name: O(2n)
  #+begin_src C++ :main no :includes :results output :exports both
    #include <iostream>
    using namespace std;

    void printItems(int n)
    {
      for (int i = 0; i < n; i++)
        {
          cout << (i + 1) << " ";
        }
      for (int j = n; j < n+n; j++)
        {
          cout << (j + 1) << " ";
        }
    }

    int main()
    {
      printItems(10);
      return 0;
    }
  #+end_src

- In terms of complexity, O(a * n) = O(n) because the effort is still
  growing linearly, at a rate of (a * n  + b).

- Visually, the curve for O(n) and for O(2n) are on top of one another
  (unless you have a constant term, which would only shift the curve
  up or down) so you won't be able to see a difference in growth rate.

* Quadratic time complexity: O(n^2)

- Change the code to nest loops inside one another:
  #+name: O(n^2)
  #+begin_src C++ :main no :includes :results output :exports both

    using namespace std;

    void printItems(int n)
    {
      for (int i = 0; i < n; i++)
        {
          for (int j = 0; j < n; j++)
            {
              cout << i << j << endl;
            }
        }
    }

    int main()
    {
      printItems(10);

* Constant time complexity: O(1)

- For this algorithm, the number of operations does not change as n
  becomes larger - it's always 1 operation (the addition):
  #+name: O(1)
  #+begin_src C++ :main no :includes :results output :exports both
    #include <iostream>
    using namespace std;

    int addItems(int n) {
      return n + n;
    }

    int main()
    {
      cout << addItems(10)  << endl;
      cout << addItems(100) << endl;
      return 0;
    }
  #+end_src

  #+RESULTS: O(1)
  : 20
  : 200

- What if we had =n + n + n= instead? That's two operations, so we get
  O(2), which we can simplify to O(1).

* Searching: O(log n)

- To find any number in a *sorted* list of *eight* numbers using *binary
  search* (splitting the data set into consecutive halves until the
  number is found), takes *three* steps: since 2^3 = 8, log_{2}(8) = 3.

- Why?  
  #+begin_quote
  Binary search on 8 elements:
  + After 1 step: 8 → 4 elements left
  + After 2 steps: 4 → 2 elements left
  + After 3 steps: 2 → 1 element left
  #+end_quote

- For very large numbers: log_2(1,073,741,824) = 30. To cut this
  number in half to get to down to one item requires 31 iterations (30
  plus one final step which we can drop).

- So the binary search algorithm on a sorted array of n elements is
  O(log n) - which really is O(log_2 n).

- On the graph, O(log n) is very close to O(1).
  #+begin_src R :file ../img/o(log_n).png :session *R* :results graphics output file :exports both

    title("Big-O: O(n^2), O(n), O(log n)")

* Sorting: O(n log n)

- The most efficient that you can make a *sorting* algorithm like merge
  sort or quick sort is O(n log n).
  #+begin_quote
  + Merge sort: split in halves, sort each half, merge.
  + Quick sort: pick a pivot, partition, sort recursively.
  #+end_quote

- Heuristic argument:
  #+begin_quote
  + Comparing unordered items needs n! possible orderings.
  + Stirling's approximation yields log_{2}(n!) \approx n log_{2} n - n.
  + Lower bound after dropping linear term: O(n log n).
  #+end_quote

- Visualized, O(n log n) is between O(n) and O(n^2):
  #+begin_src R :file ../img/o(n_log_n).png :session *R* :results graphics output file :exports both

    title("Big-O: O(n^2), O(n log n), O(n), O(log n), O(1)")
    par(new=TRUE)
    lines(x,x*x, type="l", col="steelblue",lwd=2, # O(n^2)

* PRACTICE Different terms for inputs

- *Task*: Write a function =printItems(int a, int b)= that runs two ~for~
  loops in sequence:
  1) The first loop should print numbers from =1= to =a=.
  2) The second loop should print numbers from =1= to =b=.
  3) Call the function in =main= with =a=10= and =b==10=.
  4) Run the program and confirm the output.
  5) From the result: What is the runtime complexity?

- Solution:
  #+begin_src C++ :main no :includes :results output :exports both
    #include <iostream>
    using namespace std;

    void printItems(int a, int b)
    {
      for (int i = 0; i < a; i++)
        {
          cout << (i + 1) << " ";
        }
      for (int j = 0; j < b; j++)
        {
          cout << (j + 1) << " ";
        }
    }

    int main()
    {
      printItems(10,10);
      return 0;
    }
  #+end_src

  Discussion:
  #+begin_quote
  - Looks as if this was O(n) + O(n) = O(2n) -> O(n).

  - But really, this is O(a) + O(b) = O(a + b).

  - Same for a nested loop with two variables. This is not O(n^2) but it
    is at best O(a * b).
  #+end_quote

* Vectors - start and end

- Most of what's true for vectors also applies to arrays.

- To add an item to the end of a vector, or when remove an item from
  its end, you don't have to touch any of the existing items:
  #+begin_src C++ :tangle ./src/myVect.cpp :main yes :includes <iostream> <cstdlib> <string> <fstream> <vector> :namespaces std :results output :exports both :noweb yes
    vector<int> myVect {11,3,23,7};
    <<printMyVect>>
    myVect.push_back(17); // add 17 at end
    <<printMyVect>>
    myVect.pop_back();    // remove last item
    <<printMyVect>>    
  #+end_src

- What's the complexity of ~vector~ operations ~push_back~ and ~pop_back~?
  #+begin_quote
  ~vector~ operations ~push_back~ and ~pop_back~ are O(1) because the
  function can jump in 1 step to the start/end of the ~vector~.
  #+end_quote

* Vectors - removing or inserting an element

- The first item of a ~vector~ can be retrieved with ~begin()~, which is
  an iterator to the first element of ~*this~ ([[https://en.cppreference.com/w/cpp/container/vector/begin][doc]]).
  #+begin_src C++ :tangle ./src/myVect.cpp :main yes :includes <iostream> <cstdlib> <string> <fstream> <vector> :namespaces std :results output :exports both :noweb yes
    vector<int> myVect {11,3,23,7};
    <<printMyVect>>
    cout << "\nFirst item: " << *myVect.begin();
  #+end_src

  #+RESULTS:
  : 
  : 11 3 23 7 
  : First item: 11

- We can use ~begin()~ to ~erase~ the first element - the method ~erase~
  takes an iterator as argument (so we don't need the asterisk):
  #+begin_src C++ :tangle ./src/myVect.cpp :main yes :includes <iostream> <cstdlib> <string> <fstream> <vector> :namespaces std :results output :exports both :noweb yes
    vector<int> myVect {11,3,23,7};
    <<printMyVect>>
    myVect.erase(myVect.begin());
    <<printMyVect>>
  #+end_src

- The problem is that now the new first element carries the index 1
  instead of 0, so the index needs to be shifted down for every one of
  the n-1 remaining items, which is O(n).

- The same occurs when we ~insert~ that item back at the start of the
  ~vector~:
  #+begin_src C++ :tangle ./src/myVect.cpp :main yes :includes <iostream> <cstdlib> <string> <fstream> <vector> :namespaces std :results output :exports both :noweb yes
    vector<int> myVect {11,3,23,7};
    <<printMyVect>>
    myVect.erase(myVect.begin());  // remove first item (value 11)
    <<printMyVect>>
    myVect.insert(myVect.begin(), 11); // re-insert 11 at start
    <<printMyVect>>
  #+end_src
  
- *Summary*:
  #+begin_quote
  Adding or removing operation at the start is therefore O(n) because
  of the reindexing while adding or removing from the end is O(1).
  #+end_quote

- What if we insert an item somewhere not at the start or at the end?
  #+begin_src C++ :tangle ./src/myVect.cpp :main yes :includes <iostream> <cstdlib> <string> <fstream> <vector> :namespaces std :results output :exports both :noweb yes
    vector<int> myVect {11,3,23,7};
    <<printMyVect>>
    myVect.insert(myVect.begin()+1, 99); // insert 99 between 1st and 2nd item
    <<printMyVect>>
  #+end_src

- Same for removing said element again:
  #+begin_src C++ :tangle ./src/myVect.cpp :main yes :includes <iostream> <cstdlib> <string> <fstream> <vector> :namespaces std :results output :exports both :noweb yes
    vector<int> myVect {11,3,23,7};
    <<printMyVect>>
    myVect.insert(myVect.begin()+1, 99); // insert 99 between 1st and 2nd item
    <<printMyVect>>
    myVect.erase(myVect.begin()+1); // remove 99 from 2nd position
    <<printMyVect>>    
  #+end_src

- Now, n-2 elements have to be reindexed - this is still O(n-2) ->
  O(n).

- *Summary*:
  #+begin_quote
  Inserting or removing somewhere away from the beginning or end does
  not change the situation because reindexing always introduces only a
  constant to the Big O argument: O(1/2 * n) -> O(n).
  #+end_quote

- How about *searching* or *accessing* a particular value: What if we want
  to find the value =7= in our (unsorted) ~vector~? We start with the
  first item and move down the ~vector~ until we found it. That's O(n).

- Looking up by *index* instead means that we can go directly to the
  index, so it is O(1). In R, if we perform =which(x == 7)= to get the
  index of =x= that has the value =7=, that's an O(n) operation but once
  we've got that index, using it incurs only an O(1) burden.

- Summary:
  #+begin_quote
  | Operation                   | Description                | Big O |
  |-----------------------------+----------------------------+-------|
  | ~push_back~                   | Add item to end            | O(1)  |
  | ~pop_back~                    | Remove item from end       | O(1)  |
  | ~begin()~                     | Get iterator to first item | O(1)  |
  | ~erase(begin())~              | Remove item from start     | O(n)  |
  | ~insert(begin(), value)~      | Insert at start            | O(n)  |
  | ~insert(mid-position, value)~ | Insert in middle           | O(n)  |
  | ~erase(mid-position)~         | Remove from middle         | O(n)  |
  | ~value lookup (by value)~     | Linear search              | O(n)  |
  | ~access by index~             | Random access              | O(1)  |
  #+end_quote

- There are two problems here:
  1) Printing is time-expensive because interaction with I/O devices
     is very slow and time-consuming. Switch it off.
  2) The compiler does a lot of optimization. You can switch it off to
     some extent by declaring variables ~volatile~.

- Improved example:
  1) No printing
  2) Loop in =doWork= is wrapped in a repetitive loop
  3) The measured time (for each repetition) is averaged.

  #+begin_src C++ :main yes :includes <iostream> <chrono> :results output :exports both
    #include <iostream>
    #include <chrono>
    using namespace std;
    using namespace std::chrono;

    void doWork(int n)
    {
      volatile int sink = 0; // prevent optimization
      for (int i = 0; i < n; i++)
        sink += i;
    }

    int main()
    {
      int R = 1000;   // number of repetitions
      int n = 100000; // input size
      long long total = 0;

      for (int r = 0; r < R; r++) {
        auto start = high_resolution_clock::now();

        doWork(n);

        auto stop = high_resolution_clock::now();
        total += duration_cast<nanoseconds>(stop - start).count();
      }

      cout << "Average time: " << (total / R) << " ns\n";
      return 0;
    }
  #+end_src

  : Average time: 35825 ns
